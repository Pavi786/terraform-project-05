## State Locking Architecture: Native S3 Locking (`use_lockfile = true`)
Historically, Terraform on AWS required a separate Amazon DynamoDB table with a `LockID` string attribute to prevent two engineers from running `apply` concurrently.

Starting in **Terraform 1.10+**, HashiCorp added native state locking directly to the Amazon S3 backend:
```hcl
terraform {
  backend "s3" {
    bucket       = "p05-tfstate-352458843311-ap-southeast-1"
    key          = "environments/dev/terraform.tfstate"
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true   # Native S3 concurrency locking!
  }
}
```
When enabled, Terraform uses S3 Object Conditional Writes (`If-None-Match` HTTP headers) to create an atomic lockfile (`.terraform.tfstate.lock.info`) directly in the S3 bucket without needing DynamoDB!

# Incident Runbooks (Quick Reference)

### Incident 1: Unexpected Security Group Rule Added Manually
- **Step 1:** Run `terraform plan -refresh-only` to observe the drift.
- **Step 2:** If rogue/unauthorized, run `terraform apply` to strip the unauthorized rule and restore the approved code.
- **Step 3:** If authorized, update `.tf` file to include the rule and run `terraform apply -refresh-only`.

### Incident 2: Unmanaged SQS Queue Needs Terraform Ownership
- **Step 1:** Identify queue URL: `https://sqs.ap-southeast-1.amazonaws.com/<ACCOUNT>/<QUEUE_NAME>`.
- **Step 2:** Write `import { to = aws_sqs_queue.name id = "<QUEUE_URL>" }`.
- **Step 3:** Write the matching `resource "aws_sqs_queue"` block.
- **Step 4:** Run `terraform plan` (Verify `1 to import, 0 to add, 0 to destroy`).
- **Step 5:** Run `terraform apply`.

### Incident 3: Refactoring Resource into a Child Module
- **Step 1:** Do **NOT** delete the old block or run apply.
- **Step 2:** Add `moved { from = aws_instance.web to = module.ec2.aws_instance.this }`.
- **Step 3:** Run `terraform plan` (Verify `0 to add, 0 to change, 0 to destroy`).
- **Step 4:** Commit to Git and apply cleanly.

### Incident 4: Corrupted or Lost State File
- **Step 1:** Immediately stop all CI/CD pipelines.
- **Step 2:** Inspect S3 bucket versioning for `environments/dev/terraform.tfstate`.
- **Step 3:** Download last known healthy version via AWS CLI.
- **Step 4:** Run `terraform state push <RECOVERED_FILE>`.
- **Step 5:** Run `terraform plan` to verify state matches live cloud.

### Incident 5: Corrupted EC2 Instance Needing Clean Recreate
- **Step 1:** Run `terraform plan -replace="module.ec2.aws_instance.this" -out=replace.tfplan`.
- **Step 2:** Verify only 1 replacement is planned.
- **Step 3:** Run `terraform apply replace.tfplan`.

# Senior DevOps Interview Questions & Expert Answers: Terraform Operations

### Q1: How do you detect and remediate infrastructure drift in automated CI/CD pipelines?
**Answer:** In production CI/CD, we schedule a daily or hourly pipeline running `terraform plan -refresh-only -detailed-exitcode`. If exit code is `2`, drift is present, triggering a Slack/email alert to the platform team. For non-production, an automated pipeline can re-apply the approved code. In production, an engineer reviews the diff to verify whether the drift was an emergency authorized hotfix or an unauthorized manual change.

### Q2: What is the difference between `terraform state mv` and a `moved` block?
**Answer:** `terraform state mv` is an imperative CLI command that modifies the state file immediately on the local machine. It is risky in team environments because other engineers don't have the move recorded in Git. `moved` blocks (introduced in Terraform 1.1) are declarative code tracked in Git. When any engineer or CI runner pulls the branch, Terraform automatically executes the state move during `terraform plan` without destroying resources.

### Q3: When should you use `use_lockfile = true` vs DynamoDB for S3 backend locking?
**Answer:** Starting in Terraform 1.10+, `use_lockfile = true` utilizes Amazon S3's native conditional write capabilities to enforce locking directly within the S3 bucket. This eliminates the operational overhead, IAM permissions, and cost of maintaining a separate DynamoDB table.

### Q4: What are the risks of `terraform state push`?
**Answer:** `terraform state push` forcefully overwrites the remote state in S3. If pushed with an older serial or incorrect lineage, it can desynchronize Terraform from the real infrastructure, causing subsequent applies to recreate or orphan production resources. Always back up the existing state and verify the lineage and serial number beforehand.

# Terraform Production Troubleshooting Guide

| Issue / Error | Root Cause | Solution |
|---|---|---|
| `Error: Error acquiring the state lock` | A previous apply crashed or another engineer is running `apply`. | Verify no pipeline is running, then run `terraform force-unlock <LOCK_ID>`. |
| `Resource already exists` during apply | Resource was created manually outside Terraform. | Import the resource using an `import {}` block or delete the manual resource. |
| `Plan proposes destroy and recreate` | An argument that does not support in-place update was modified (e.g., changing VPC ID or subnet). | Check if change is intended or use `create_before_destroy = true` to minimize downtime. |
| `Error: Provider configuration not present` | A module uses a provider alias that wasn't passed down. | Add `configuration_aliases` to module `versions.tf` and pass the alias from root. |

# Lab 01 – Infrastructure Drift Detection & Remediation

## 1. Real-World Production Incident
**Incident Ticket #INC-9481:**  
*Severity:* P1 - Security Compliance Violation  
*Summary:* An on-call engineer troubleshooting an off-hours connectivity alert manually opened inbound rules directly inside the AWS Console. Two days later, an automated security audit flagged that an internal database/application port was left wide open to unapproved CIDRs. When a colleague attempted to run a planned Terraform release, unexpected drift was detected.

---

## 2. Architecture & Concept
```text
  [Approved IaC Code]               [Terraform State]               [Real AWS World]
   (environments/dev)             (S3 Remote Backend)              (ap-southeast-1)
           │                               │                              │
           │                               │                              │
    Port 443 only                   Port 443 only               Manual Console Edit:
   (from 10.0.0.0/16)              (from 10.0.0.0/16)          [Port 443 from 10.0.0.0/16]
           │                               │           + [Unapproved Port 8080/443]
           │                               │                              │
           └───────────────────────────────┼──────────────────────────────┘
                                           │
                                           ▼
                             `terraform plan -refresh-only`
                                  (Detects the Drift)
```

---

## 3. Layman Explanation
Imagine a company's building blueprint (Terraform code). The building manager keeps a copy of the blueprint in the archive (State file). One weekend, a maintenance worker punches a hole in the wall to run a temporary cable, but forgets to tell anyone.  
- **Drift** is the difference between the blueprint and the actual building.  
- `terraform plan -refresh-only` is like sending an inspector with a clipboard to look at the physical building and compare it with the state file without touching or demolishing anything.  
- If you run `terraform apply`, Terraform repairs the wall back to blueprint specifications.  
- If you run `terraform apply -refresh-only`, Terraform updates the blueprint to say "the hole is officially accepted".

---

- Does **not** open SSH (Port 22) or `0.0.0.0/0` inbound.
- Controlled test target that can be safely modified manually in the console to practice drift.

## 6. Interview Questions & Expert Answers

**Q1: What is the difference between `terraform plan` and `terraform plan -refresh-only`?**  
*Answer:* `terraform plan` compares the `.tf` code against the real world and proposes changes to bring AWS in line with code. `terraform plan -refresh-only` only queries AWS to detect what changed outside Terraform, and proposes updating the **state file** to match the real world, without proposing any changes to AWS resources.

**Q2: What is the risk of running `terraform apply -refresh-only` blindly?**  
*Answer:* If an attacker or rogue engineer added malicious ingress rules (e.g. `0.0.0.0/0` on SSH/RDP), running `-refresh-only` accepts that malicious change into your state file instead of wiping it out. Always review drift diffs carefully.

---

## 7. Cost & Security Review
- **Cost:** Security Groups have **$0.00** hourly or monthly charges in AWS.
- **Security:** Never leave `0.0.0.0/0` open on management ports. Lab uses isolated test CIDRs.

# Lab 02 – Importing Existing AWS Resources

## 1. Real-World Production Incident
**Incident Ticket #INC-1022:**  
*Summary:* An infrastructure component (an SQS dead-letter queue) was provisioned manually via AWS Console during a production hotfix. The team now requires all cloud infrastructure to be 100% managed under Terraform. We must bring the existing queue into Terraform state **without destroying or recreating it**, as active messages are in flight.

---

## 2. Concept & Methods
Terraform offers two approaches to importing:
1. **Modern Declarative `import` block (Terraform 1.5+):** Code-first, reviewable in pull requests, generates template code.
2. **Traditional CLI `terraform import`:** Imperative command updating state directly.

### Modern Import Block (Recommended)
```hcl
import {
  to = aws_sqs_queue.orders_dlq
  id = "https://sqs.ap-southeast-1.amazonaws.com/352458843311/p05-unmanaged-orders-dlq"
}

resource "aws_sqs_queue" "orders_dlq" {
  name                      = "p05-unmanaged-orders-dlq"
  message_retention_seconds = 86400
}
```

---

## 3. Terminal Execution Sequence
1. Create target SQS queue in AWS Console or via AWS CLI.
2. Add the `import` block and matching `resource` block.
3. Run `terraform plan`:
   *Expected:* `Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.`
4. Run `terraform apply`:
   Imports the resource directly into S3 remote state.

# Lab 03 – Refactoring with Moved Blocks

## 1. Real-World Production Incident
**Incident Ticket #INC-2045:**  
*Summary:* A monolithic Terraform configuration defined `aws_instance.web`. The team is standardizing on a reusable `modules/ec2` module. Simply changing the code address from `aws_instance.web` to `module.ec2.aws_instance.this` would normally cause Terraform to **destroy the production server and create a brand new one** (causing downtime and data loss).

---

## 2. Solution: The Declarative `moved` Block (Terraform 1.1+)
Instead of manual, risky `terraform state mv` commands run out-of-band by developers, Terraform allows declarative `moved` blocks tracked in Git:

```hcl
moved {
  from = aws_instance.web
  to   = module.ec2.aws_instance.this
}
```

When you run `terraform plan`:
```text
Terraform will perform the following actions:

  # aws_instance.web has moved to module.ec2.aws_instance.this
    resource "aws_instance" "this" {
        id = "i-0123456789abcdef0"
        # (all attributes preserved)
    }

Plan: 0 to add, 0 to change, 0 to destroy.
```
**Zero downtime. Zero recreation. The EC2 instance ID stays exactly the same!**

# Lab 04 – Terraform State Backup & Disaster Recovery

## 1. Real-World Production Incident
**Incident Ticket #INC-3109:**  
*Summary:* A CI/CD pipeline job failed midway through a state migration, or an engineer corrupted the remote state file. Terraform now throws parse errors or reports that all production resources no longer exist.

---

## 2. Disaster Recovery Checklist
1. **Never panic and never run `terraform apply`** on an empty state (it will recreate duplicate resources or orphan live infrastructure).
2. Leverage S3 Bucket Versioning:
   ```bash
   aws s3api list-object-versions \
     --bucket <STATE_BUCKET> \
     --prefix environments/dev/terraform.tfstate \
     --region ap-southeast-1
   ```
3. Download the last known good version:
   ```bash
   aws s3api get-object \
     --bucket <STATE_BUCKET> \
     --key environments/dev/terraform.tfstate \
     --version-id "<LAST_KNOWN_GOOD_VERSION_ID>" \
     recovered_state.json
   ```
4. Verify Lineage & Serial:
   Every state file has a `lineage` GUID and an incrementing integer `serial`.
5. Restore using `terraform state push`:
   ```bash
   terraform state push recovered_state.json
   ```

# Lab 05 – Safe EC2 Resource Replacement

## 1. Real-World Production Incident
**Incident Ticket #INC-4420:**  
*Summary:* An EC2 instance has an unhealthy OS filesystem corruption or compromised kernel, but its Terraform configuration hasn't changed. Running `terraform apply` reports `No changes`. How do we force a controlled, safe recreation without modifying `.tf` code?

---

## 2. Command: `terraform apply -replace`
Instead of the deprecated `terraform taint`, modern Terraform uses:

```bash
terraform plan -replace="module.ec2.aws_instance.this" -out=replace_plan.tfplan
```

*Expected Output:*
```text
Terraform will perform the following actions:

  # module.ec2.aws_instance.this will be replaced, as requested
-/+ resource "aws_instance" "this" {
      ~ id = "i-old12345" -> (known after apply)
      ...
    }

Plan: 1 to add, 0 to change, 1 to destroy.
```

Applying the saved plan:
```bash
terraform apply replace_plan.tfplan
```
---

## 3. Minimizing Downtime: `create_before_destroy`
In lifecycle configuration:
```hcl
lifecycle {
  create_before_destroy = true
}
```
Terraform launches the new healthy instance **first**, waits for AWS confirmation, and only then terminates the old instance.
